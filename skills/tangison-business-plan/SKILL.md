# Tangison Business Plan

## Purpose

Create a truthful, decision-ready plan that separates facts, assumptions, estimates, projections, recommendations, missing information, and rejected claims.

**A completion claim without evidence is invalid.**

## Use this skill when

- A new or revised business plan is required.
- A funding or investment narrative needs structured reasoning.
- Existing plan claims or assumptions need correction.

## Do not use this skill when

- Do not own final visual PDF construction.
- Do not invent market size, demand, competitors, employment, revenue, costs, approval probability, qualifications, regulation, or property values.
- Do not hide missing information inside persuasive prose.

## Ownership

This skill owns business-plan reasoning and narrative architecture. Research owns facts; Financial Model owns calculations; Documents or Magazine owns final layout.

## Required inputs

- Verified business facts, legal structure, ownership, offering, geography, audience, and funding purpose.
- Research ledger, operating evidence, pricing, cost inputs, and financial model.
- Named institution requirements when funding is in scope.
- Missing and rejected claims.

## Inputs to inspect first

1. Read the complete current request.
2. Read approved project files and authentic source assets.
3. Read repository instructions and inspect the current state when code or files are involved.
4. Read **BUILD_PLAN.md** and **PROOF.md** when present.
5. Inspect available capabilities before declaring a tool or check unavailable.

## Assumptions and authority gates

- Stop when ownership, legal structure, funding amount, use of funds, regulated activity, or a material financial assumption is unresolved.
- Do not imply lender approval.
- Record every material assumption. Never present an assumption as a verified fact.
- Ask one concise question only when the answer materially changes scope, ownership, legal meaning, cost, public release, production state, or an irreversible action.
- Never expose credentials or place them in source, URLs, logs, evidence, or handoff files.

## Required tools and fallbacks

- Use current primary Namibian sources when Namibia is in scope.
- Maintain a classification ledger for every material statement.
- Keep financial source data machine-readable.
- When a required capability is unavailable, use the nearest safe supported method and record the missing verification.
- Never invent a tool result, browser result, build result, deployment result, or remote state.

## Procedure

1. Classify all inputs as verified, supplied, assumed, estimated, projected, recommended, missing, or rejected.
2. Define the plan objective and reader decision.
3. Build sections for executive summary, company, ownership, opportunity, offering, market, competition, model, pricing, operations, staffing, marketing, sales, implementation, risks, funding, use of funds, assumptions, and supporting documents where relevant.
4. Route unstable facts to Research.
5. Route all calculations to Financial Model.
6. Tie recommendations to evidence and implementation capacity.
7. State risks and mitigations without hiding uncertainty.
8. Create an approval and missing-information checklist.
9. Cross-check narrative figures against the model.
10. Hand locked content to the document owner.

## Verification

- Every material claim has a classification and source or assumption.
- Narrative figures match the financial model.
- Funding need and use of funds reconcile.
- Risks and missing information are explicit.
- No invented approval, demand, market, or performance claim remains.
- Run verification after the latest material change.
- Separate action, observed result, evidence, interpretation, and remaining risk.

## Proof requirements

Maintain **PROOF.md** for material work using:

Phase | Action | Target | Command or method | Result | Evidence path or URL | Timestamp | Status

Use only these working statuses: planned, running, passed, failed, blocked, paused, superseded.

The following are not proof: a file merely existing, a claim that work should function, a check run before the latest change, a local commit without remote verification, or a different test replacing the failed test.

## Failure and debugging procedure

1. Reproduce the failure with the same input and command or method.
2. Preserve the failing output and evidence path.
3. Identify the root cause. Do not replace diagnosis with a guess.
4. Apply the smallest complete correction within the authorised scope.
5. Rerun the exact failed check, then run the relevant regression checks.
6. Record the failure, correction, new result, and remaining risk in `PROOF.md`.

## Completion gate

Do not claim completion until:

- every approved output exists and matches the locked scope;
- the latest applicable checks pass;
- **PROOF.md** contains real evidence;
- unauthorised or unrelated work is absent;
- remaining risk and blocked checks are disclosed.

## Handoff

Return the complete plan content, fact and assumption ledger, model references, funding-use reconciliation, missing documents, and layout instructions.
