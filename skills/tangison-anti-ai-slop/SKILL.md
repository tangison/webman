# Tangison Anti-AI Slop

## Purpose

Force reference-led, organisation-specific art direction and reject visual clichés, fake evidence, and layouts that could belong to any brand.

**A completion claim without evidence is invalid.**

## Use this skill when

- A visual concept or layout is being chosen.
- Generated imagery will support a real organisation.
- A design feels generic, decorative, or over-produced.
- Final visual work needs an independent structural critique.

## Do not use this skill when

- Do not clone a competitor or protected expression.
- Do not fabricate clients, staff, awards, metrics, testimonials, or results.
- Do not treat trend familiarity as brand relevance.

## Ownership

This skill owns the anti-slop gate. The named art-direction owner still controls the final design system.

## Required inputs

- Approved brand facts and authentic assets.
- One relevant industry reference, one typography or editorial reference, and one composition or interaction reference when browsing is available.
- Target format, audience, and focal action.

## Inputs to inspect first

1. Read the complete current request.
2. Read approved project files and authentic source assets.
3. Read repository instructions and inspect the current state when code or files are involved.
4. Read **BUILD_PLAN.md** and **PROOF.md** when present.
5. Inspect available capabilities before declaring a tool or check unavailable.

## Assumptions and authority gates

- If reference research is unavailable, state that limitation and do not invent inspected examples.
- Stop when an official logo or factual visual source is missing and substitution would misrepresent the client.
- Record every material assumption. Never present an assumption as a verified fact.
- Ask one concise question only when the answer materially changes scope, ownership, legal meaning, cost, public release, production state, or an irreversible action.
- Never expose credentials or place them in source, URLs, logs, evidence, or handoff files.

## Required tools and fallbacks

- Use supplied references first.
- Use browsing for current visual references when available.
- Inspect final work at full size, target viewport, thumbnail size, and monochrome where relevant.
- When a required capability is unavailable, use the nearest safe supported method and record the missing verification.
- Never invent a tool result, browser result, build result, deployment result, or remote state.

## Procedure

1. Create a reference ledger with source, useful principle, permitted abstraction, and prohibited copying.
2. Define one design idea tied to the organisation.
3. Set hierarchy and one focal point.
4. Remove decorative elements without purpose.
5. Reject default purple-blue gradients, random glow, glass panels, blobs, meaningless grids, excessive pills, repeated rounded cards, arbitrary heading lines, fake metrics, and generic black-gold treatment.
6. Check that typography, image crops, material, spacing, and motion express the chosen idea.
7. Ask whether the same design would fit an unrelated organisation after only changing the logo.
8. If yes, revise the concept.
9. Run the structural test again before handoff and record evidence.

## Verification

- The reference ledger is real and source-backed.
- The design idea connects to the specific organisation.
- Hierarchy and focal point are unambiguous.
- No fabricated proof or generic filler remains.
- The unrelated-company substitution test fails, meaning the work is specific.
- Run verification after the latest material change.
- Separate action, observed result, evidence, interpretation, and remaining risk.

## Proof requirements

Maintain **PROOF.md** for material work using:

Phase | Action | Target | Command or method | Result | Evidence path or URL | Timestamp | Status

Use only these working statuses: planned, running, passed, failed, blocked, paused, superseded.

The following are not proof: a file merely existing, a claim that work should function, a check run before the latest change, a local commit without remote verification, or a different test replacing the failed test.

## Failure and debugging procedure

1. Reproduce the failure with the same input and command or method.
2. Preserve the failing output and evidence path.
3. Identify the root cause. Do not replace diagnosis with a guess.
4. Apply the smallest complete correction within the authorised scope.
5. Rerun the exact failed check, then run the relevant regression checks.
6. Record the failure, correction, new result, and remaining risk in `PROOF.md`.

## Completion gate

Do not claim completion until:

- every approved output exists and matches the locked scope;
- the latest applicable checks pass;
- **PROOF.md** contains real evidence;
- unauthorised or unrelated work is absent;
- remaining risk and blocked checks are disclosed.

## Handoff

Return the design idea, reference ledger, removed generic patterns, inspection evidence, and remaining visual risks.
